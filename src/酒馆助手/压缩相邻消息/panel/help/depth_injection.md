# 处理条目

本脚本提供三种条目处理方式:

- 无: 不额外提取条目
- 处理 D⚙ 条目: 使用原有规则处理深度条目
- 处理世界书条目: 提取本轮实际激活并注入最终提示词的世界书条目

## 处理世界书条目

该模式监听酒馆的世界书激活结果，搬运本轮实际进入提示词的正文，并回放符合当前规则的绿灯缓存。

### 提取规则

规则从界面最下方开始向上匹配，尚未处理的内容继续交给上方规则。每条规则包含筛选条件和放置策略：

“添加规则”创建通用规则；“添加内置规则”打开单选模板库，向列表底部添加一份独立、可编辑的模板副本。模板库与已保存的规则列表分别管理。

- 规则类型：通用世界书规则，或 RUBY、柏宝书的专属内容分类。以下来源、表达式与触发条件用于通用世界书规则。
- 来源：角色世界书、角色可选世界书、聊天世界书、用户世界书和全局世界书，多选之间为“或”。用户世界书指用户人设绑定的世界书。同一世界书可以同时属于多个来源，条目只处理一次。
- 匹配对象：世界书名称、条目标题或条目原始正文。
- 匹配表达式：支持 `/表达式/标记` 或直接填写表达式；留空表示不限。正则捕获组只参与筛选。
- 触发方式：全部、常驻、关键词。常驻对应蓝灯，关键词对应绿灯。
- 内容特征：全部、仅静态、仅动态，与触发方式独立筛选。
- 处理方式：提取到提取词，或保留原位。保留原位命中后停止应用上方规则。
- 提取词：例如 `story_archive` 对应 `{{压缩相邻消息::story_archive}}`。 `{{压缩相邻消息::lora_custom::story_archive}}`
  是同一提取词的另一种写法。
- 优先固定绿灯缓存：本组捕获的非动态绿灯优先固定到首次触发楼层，其余内容送入提取词。

同一规则的不同筛选条件需同时满足。普通提取要求本轮提示词存在对应占位符；目标缺失时继续尝试上方规则。相同提取词的内容会跨规则统一排序后合并。已配置的占位符本轮没有提取结果时替换为空。选择条目正文作为匹配对象时，匹配用于筛选整个来源条目，提取正文仍以实际展开结果为准。

默认规则包括静态蓝灯、绿灯、动态蓝灯和黑科技世界书规则：静态蓝灯进入 `lora_constant`，绿灯与动态蓝灯共用
`lora_key`，标题匹配 `/TavernDB-ACU-(.*)/gi` 的条目优先进入 `sp_memory`。

### 插件专属规则

- RUBY 分析输出：读取当前角色生效方案的开局任务及各任务 `outputKey`，匹配当前聊天绑定世界书中的主关键词。同书同输出键的条目分别保留身份、统一归组。附加触发词继续由酒馆处理。
- 柏宝书历史摘要、当前状态、向量召回和时间标签指令：分别匹配柏宝书的四个专属扩展注入槽。模板的提取词为 `bbs_history`、`bbs_state`、`bbs_recall` 和 `bbs_instructions`；时间标签指令模板默认保留原位。

专属规则使用本次请求中的实际内容，不进入固定绿灯缓存。提取后的位置和角色由占位符所在提示词决定；目标不存在或正文无法唯一定位时保持原位。

### 内容分析

扫描阶段只读收集原文快照，通过条目指纹和激活对象关联生成结果。条目边界在本次请求中建立，模板展开后再完成提取、回填和 Debug 记录；不会重新扫描关键词。无法安全定位的动态正则改写结果保留原位。

动态宏按原始世界书正文判断. `<USER>`、`<BOT>`、`<CHAR>`、`{{user}}`、`{{char}}` 不会被视为动态宏; 纯输出形式的
`<%- await getwi(...) -%>` / `<%= await getWorldInfo(...) %>` 也不会被视为动态宏; 参数只接受静态字符串、数字或
`null`. 除此之外的 `{{...}}` 或 EJS 模板标签会被视为动态宏.

蓝灯持久条目中的安全 `getwi` 会最多递归判定 3 层. 如果第 3 层后仍有
`getwi`, 或目标找不到、同名多匹配、循环引用, 会按动态内容处理. 如果蓝灯持久条目除空白外只包含多个安全
`getwi`, 则静态目标会单独提取到 `{{压缩相邻消息::lora_constant}}`, 动态目标会单独提取到
`{{压缩相邻消息::lora_key}}`; 匹配不到本轮提示词中的实际展开内容时, 会保留在原位置, 不会凭空注入. 临时包裹只存在于本次请求中，未消费的边界会在发送前剥除。

### 固定绿灯缓存

规则开启“优先固定绿灯缓存”后，具有缓存资格的绿灯会进入固定楼层区域，不再重复进入提取词区域。该路径无需提取占位符。快照保存在当前聊天变量
`压缩相邻消息.绿灯缓存`，固定到首次触发时的真实楼层和 swipe 后方，并在处理聊天历史前参与合并。后续无需再次触发关键词，仍可回放有效快照。缓存回放会重新检查当前规则归属；被其他普通提取规则接管时暂停回放，记录保留。

激进处理绿灯缓存只处理真正的绿灯条目, 不处理蓝灯或向量化条目. 绿灯中的 `getwi`
按动态内容处理。缓存会记录世界书名、条目 uid、条目名、原始正文 hash 和实际注入内容快照。楼层、swipe 被删除或正文 hash 变化时，旧快照失效；条目停用或锚点楼层隐藏时暂停回放，重新可用后沿用有效锚点。关闭该选项不会清理缓存，可使用“清空绿灯缓存”按钮清理当前聊天变量中的缓存。

排序默认按以下顺序:

- 角色定义前
- 角色定义后
- 示例消息前
- 示例消息后
- 作者注释前
- 作者注释后
- D⚙ 消息

D⚙ 消息内部按插入深度排序, 深度越大越靠前. 同级条目按优先级排序, 优先级越大越靠后.

## 处理 D⚙ 条目

按照[一些预设作者和角色卡作者的说法](https://discord.com/channels/1134557553011998840/1413538722078785576),
Gemini 和 Claude 不同, 不必将条目插入聊天记录中, 插入其中反而会干扰聊天记录的连续性, 重要条目应该都插入到 D0.

但玩家依旧可能使用 Claude、GPT 等游玩, 而对它们还是需要用 D4 等深度的.

因此本脚本提供了处理深度条目功能, 允许你特殊处理特定深度 (Dx) 以上和以下的系统深度条目 (D⚙ 条目):

- 将它们按顺序插入到 D9999/D0: 如果说法无误, 几乎所有预设都能从中获得好处, 而不会产生负面影响
- 或将它们合并成一条文本, 并替换到占位符位置: 预设可以赋予这些条目特殊的语义, 就像有的预设为 AI 把 "角色定义之前/之后" 部分定义成
  `additional_settings` 那样

---

**注意**: 这些选项虽然已经不用角色卡作者自行将条目全设置为 D0，但仍很需要角色卡适配；如果角色详情等会随剧情发展的设定放在了深度条目，则勾选这些选项容易使角色固化。
